## Objective

Complete **S3-01–S3-04** and **MON-01–MON-03** from Section 5.7. Member 3 verifies data security; Member 4 verifies monitoring, coordinating with Members 1 and 2 for networking and EC2 commands.

Use the deployed configuration without broadening permissions to force success. Record Pass/Fail using actual evidence.

## Prerequisites

- Complete 5.7.1, remove the temporary NACL rule, and restore website operation.
- Record the Instance ID, actual bucket, **ap-southeast-1**, **WorkshopEC2AppRole**, **s3-gateway-endpoint**, and **rtb-web-public**.
- The script from 5.5.3 is installed at `/opt/document-portal/ec2-s3-check.py` on EC2. If missing, transfer it again using 5.5.3; do not substitute an unreviewed script.
- Prepare non-sensitive sample objects and assigned Console read permissions for S3, IAM, VPC, and CloudWatch. Console user permissions differ from EC2 instance-profile permissions.
- **workshop-web-01-cpu-high**, **/workshop/webserver**, and **INSTANCE_ID/application** are configured.

## Step 1: Verify identity and permission scope

1. Open **EC2 → Instances → workshop-web-01 → Security** and verify **WorkshopEC2AppRole** is attached.
2. In IAM, inspect the role policies. Expected S3 scope: ListBucket conditioned on `portal/`, and GetObject/PutObject for `portal/*` in the correct bucket.
3. Review inline policies, managed policies, and the bucket policy. A narrow policy does not cancel broader permissions granted elsewhere.
4. Preserve the log-writing policy from 5.6.3. Do not change roles or create access keys for testing.


## Step 2: Test allowed and denied access — S3-01, S3-02

On EC2, run the script as the service user in a clean environment:

```bash
sudo -u portal env -i \
  PATH=/usr/bin:/bin HOME=/nonexistent \
  AWS_SHARED_CREDENTIALS_FILE=/dev/null AWS_CONFIG_FILE=/dev/null \
  /opt/document-portal/.venv/bin/python /opt/document-portal/ec2-s3-check.py
```
The script reads the configured bucket, requires instance-profile credentials, and checks the role in Caller ARN. It does not print passwords, password hashes, or access keys.

| Script operation | Required result |
| --- | --- |
| List portal/ | LIST portal/: PASS |
| Create a random portal/ec2-check-...txt object | Successful PutObject |
| Read back and verify bytes/SSE-S3 | PUT/GET/SSE-S3: PASS and SHA256 |
| List outside/ | PASS (AccessDenied) |
| Delete the newly created disposable object | PASS (AccessDenied) |

**Deletion test:** Only the object created by this execution is used. Excessive permissions may allow its deletion, causing FAIL. Never substitute a real document key. If the outside/ listing unexpectedly succeeds, the script stops before deletion; mark deletion as not executed.

1. Record Caller ARN, bucket, test key, and execution time.
2. Mark S3-01 Pass only when list/read/write and content verification succeed.
3. Mark S3-02 Pass only when **both** out-of-scope operations return AccessDenied.
4. Timeouts, DNS errors, missing credentials, or STS failures are not AccessDenied. STS uses the existing HTTPS Internet path, not the S3 Gateway Endpoint.
5. On FAIL, stop and review all permissions. Do not change the script's expected outcome. Retain remaining test objects for administrator cleanup in 5.8.

## Step 3: Test anonymous access — S3-03

1. In **S3 → bucket → Objects → portal/**, select an existing sample object. Confirm the data operator can download it with valid authorization.
2. Copy its **ordinary Object URL**, not Share with a presigned URL or a signed URL generated by Open/Download.
3. Verify there are no signature parameters such as `X-Amz-Signature`, `X-Amz-Credential`, or `X-Amz-Security-Token`. Use HTTPS and the correct Region.
4. Open it in a private browser window without signing in. Expect **403 AccessDenied** and no document contents.
5. If it downloads, check that the URL is unsigned and review public permissions/bucket policy. DNS errors, timeouts, wrong-Region redirects, or a nonexistent key are insufficient evidence of success.

Presigned URLs grant temporary access; successfully opening one does not imply a public bucket. Authenticated website access and anonymous S3 access are different flows.

## Step 4: Verify storage security — S3-04

1. Under bucket **Permissions**, verify all four **Block Public Access** settings and **Object Ownership = Bucket owner enforced**, with ACLs disabled.
    ![](/FCAJ_Worklog/images/kiemthu/41.png)
   ![](/FCAJ_Worklog/images/kiemthu/42.png)
   ![](/FCAJ_Worklog/images/kiemthu/43.png)
2. Review the HTTPS-only bucket policy from 5.5.3. Do not remove it to bypass errors.
3. Under **Properties → Default encryption**, verify **SSE-S3**.
4. Select an object uploaded through the website in 5.7.1 → **Properties → Server-side encryption**, and verify SSE-S3 on that object. Bucket defaults do not replace inspection of the actual object.
5. Record the bucket/key and results. Reviewing the HTTPS-only policy is a configuration check, not proof of testing a signed HTTP request.



## Step 5: Verify the S3 Gateway Endpoint configuration — S3-04

1. Record the instance's subnet/VPC in EC2.
2. Open **VPC → Subnets → actual subnet → Route table** to identify its effective route table, rather than relying on Name tags.
3. Open **Endpoints → s3-gateway-endpoint** and verify the VPC, **Gateway** type, **com.amazonaws.ap-southeast-1.s3** service, and **Available** status.
4. Verify the endpoint's Route tables include the EC2 subnet's effective table.
5. In that table, verify Singapore S3 `pl-...` → endpoint `vpce-...`. Preserve the local route and `0.0.0.0/0 → igw-...` Internet route.
6. Verify the bucket is in the same Region and the application uses the ordinary regional S3 endpoint, without an out-of-design custom endpoint/proxy.

This is **routing configuration verification combined with an EC2 S3 test**, not a per-request traffic trace. S3 DNS may return public IPs even when routing uses a Gateway Endpoint. A successful laptop download or traceroute alone is insufficient evidence. Do not detach routes/endpoints or add SourceVpce deny policies just for this test.

## Step 6: Verify CPU metrics and alarms — MON-01, MON-02

1. Open **CloudWatch → Metrics → All metrics → EC2 → Per-Instance Metrics**.
2. Select CPUUtilization for the correct InstanceId, using **Average**, **5 minutes**, and a range with recent data. Record timestamps/time zone.
3. Open **Alarms → workshop-web-01-cpu-high**. Verify Instance ID, **>80%**, **300 seconds**, **2/2**, and **missing** data treatment.
4. Open **History** for the 5.6.2 test window. Verify ALARM was based on breaching datapoints and recovery to OK followed the end of the load.
5. Reuse 5.6.2 evidence only if resources/settings are unchanged, recording its original timestamp. If evidence is missing or relevant settings changed, repeat the bounded procedure from 5.6.2 after checking credits. Do not run unlimited load.
6. If SNS is used, verify the email matches the alarm/time. Otherwise mark email Not applicable.

Current OK alone does not establish that ALARM was tested. Manual SetAlarmState does not prove a CPU breach. INSUFFICIENT_DATA is not a healthy state. Finish by confirming the load has stopped and the website works.

## Step 7: Verify new application logs — MON-03

1. Record the start time. On the HTTPS website, submit one wrong password, sign in correctly, upload/download a sample document, and sign out. Avoid repeated failures because of rate limiting.
2. Check the application logs on EC2:

```bash
date -u
sudo tail -n 50 /var/log/document-portal/application.log
sudo /opt/aws/amazon-cloudwatch-agent/bin/amazon-cloudwatch-agent-ctl -a status
```

3. Open **CloudWatch → Logs → Log groups → /workshop/webserver → INSTANCE_ID/application**, choose a range covering the test, and Refresh.
4. Find `login_failed`, `login_success`, `upload_success`, `download_success`, and `logout`. Correlate messages/times with EC2 and clear filters between searches.
5. Distinguish the message timestamp from agent read/delivery time; exact equality is not required. Check UTC versus UTC+7.
6. Confirm 7-day retention and no passwords, cookies/tokens, access keys, or document contents in logs.

A running agent or existing old logs is insufficient: find **new events matching this test**. If absent, check the local file, agent configuration, log-writing permissions, and HTTPS connectivity to CloudWatch Logs as in 5.6.3. Making the S3 bucket public cannot fix log delivery.

## Results and troubleshooting

| ID | Criteria | Actual status |
| --- | --- | --- |
| S3-01 | Correct role; list/read/write portal/; matching contents | Pass |
| S3-02 | Outside-prefix list and disposable-object delete return AccessDenied | Pass |
| S3-03 | Unsigned object URL rejects anonymous access | Pass |
| S3-04 | Secure bucket/object settings and correct endpoint routing | Pass |
| MON-01 | Recent CPU data for the correct Instance ID |Pass |
| MON-02 | Appropriate ALARM and recovery evidence | Pass |
| MON-03 | New events match actions; 7-day retention | Pass |

For AccessDenied on read/write, inspect the role, bucket/prefix, and applicable policies. If out-of-scope access succeeds, look for broader grants across all relevant policies. For timeouts, check networking first. For missing logs, distinguish application logging failures from agent delivery failures.

Use the Section 5.7 results template with tester, time, resources, evidence, and failure causes/fixes. Save **8 screenshot locations**; do not mark unexecuted tests Pass. Do not publish credentials, presigned URLs, or other secrets.
